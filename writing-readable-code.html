3  Writing readable code

“Programs must be written for people to read, and only incidentally for machines to execute.”

– Harold Abelson and Gerald Jay Sussman, Structure and Interpretation of Computer Programs

So far we have focussed on structural things I would class as “easy wins” - where things live, creating projects, file paths and reproducibility, style linting, and a README. Something I really appreciate is how tools like {air}/{styler} and {jarl}/{flir} make this easy and repeatable.

Now let’s talk about something that is a bit more of a skill - how to write readable code. We work on one script the whole way through. First the names, then the code, then how to do this to somebody else’s work without it going badly.

Duration 60 minutes

Questions

3.1 Clean as you go

There is one core idea I’d like to get across this chapter:

You won’t write your best code on the first pass.

Just like writing, I don’t write my best code on the first pass. Your code gets better as you review it. The first pass is for getting it working, mostly. After that, you are improving readability, and expression.

To add another analogy into the mix: Professional kitchens clean as they go, because a tidy bench keeps your mind clear and because the alternative is chaos by service.

So, I think when you finish a piece of work, it would serve you well to go back over it briefly:

  • Clean up the comments that no longer mean anything.
  • Remove the “wilted lettuce”1.
    • The commented-out chunks of code you might just come back to
    • You probably won’t come back to these bits
    • If one really matters, write a comment saying why, rather than leaving it lying there.
  • Fix the style (use air or styler).
  • Check the names.
  • Make any notes about weirdness/strangeness/slowness

Now, you can’t do a full review of your code, all the time.

But doing some of it will make your code better - and you’ll get faster at it the more you practice.

Let’s talk about how to do this.

3.2 The script

Imagine that someone hands you a script. It runs, it makes a plot at the end, and they would like another year of data added to it. Today, ideally.

Here’s the script! Don’t read it closely yet. Scroll through it. What do you notice?

This is a real script of mine, from a project called ozed that I used for an example project when teaching.

The goal of the analysis was to look at how many Australians are studying, by age group and by state, using data from the Australian Bureau of Statistics.

I want to be fair to it, because it is not bad code.

It runs. It’s formatted. A linter has almost nothing to say about it. It even has comments. By the standards of everything in this book so far, it passes.

But I think we can do better.

Here’s a few things wrong with the code:

  1. The names tell you nothing. x1, x2, y1, y2, z.
  2. Two of the functions in it might not be the ones you think. filter() is in there. There are two functions called filter(), and which one you get depends on the order of those six library() calls.
  3. It is a wall of text. There isn’t much guidance.

We shall look at these now, in that order.

3.3 Bad, better, and good variable names

There is a quote attributed to Phil Karlton:

There are only two hard things in computer science: cache invalidation and naming things.

CautionSome history: where the quote comes from

Phil Karlton was a principal developer at Xerox PARC, DEC, Silicon Graphics and Netscape. Martin Fowler has written up the provenance of the quote, which is more interesting than you’d expect. Nobody has ever found where Karlton first said it, and it seems to have travelled by word of mouth from about 1996.

It’s comforting to know that naming things is genuinely hard. I think we can sometimes let perfect become the enemy of good - we can combat this by saying:

giving things an OK name is much easier than giving things a great name.

If we can aim to make the names a little better - even just “OK”, then that’s good progress.

Here’s a little demo of some names of four things:

  1. a data frame read off disk,
  2. that data frame with one island kept,
  3. a model,
  4. and a plot.
Bad OK Good
d penguins penguins_raw
df2 penguins_filtered penguins_biscoe
m model lm_mass_by_species
p1 mass_plot boxplot_mass_species

When you come across the names in the bad column, you usually have to refer back the script to see what they were and how they were used. df2 could be anything. So could m.

The OK column does not cost you that trip back to the script, as much.

  • penguins_filtered doesn’t tell me which filter. I am OK with that because it tells me: “this is the penguin data, and it has been filtered”.

The good column is better again.

Notice the gap between bad and OK is much wider than the gap between OK and good.

It’s OK to aim for OK.

As you practice giving OK names to things, you’ll get more practice at naming, and get better. But don’t put too much into it.

3.3.1 A bit more on OK names

How do give things OK names?

Say what it holds, in two or three words, joined by _. If a better name shows up later, rename it then.

A name isn’t a commitment! You can rename easily, and there’s some good tricks.

You can do:

  • Find + replace (Cmd/Ctrl + F)
  • Find all (Cmd/Ctrl + Shift + F)
  • Rename in scope (Cmd / Ctrl + Shift + Alt + M) with your curstor on the name.

Or search any of those in the command palette.

NoteYour Turn: rename the script

The script is 10-hard-to-read/analysis.R in the course repo, or copy it out of the listing above. Either way, it has eight badly named objects in it: d, n1, n2, x1, x2, y1, y2 and z.

  1. Rename them. Five seconds each. OK names, not great ones, and don’t stop to admire any of them.
  2. Use Rename in Scope (Cmd / Ctrl + Shift + Alt + M) or F2, not find and replace. Find and replace on a name like d will do something you did not want.
  3. Read the script again afterwards. How much of it can you now follow without scrolling back up?
  4. One question I actually want an answer to: what is n2, and why are there two of them?

That last one is the interesting bit, so don’t skip it. Something becomes visible when the names are fixed that was invisible before, and it was in my real script, not something I planted.

::: {.callout-tip title=“And the answer to n2”, collapse=“true”}

With the names put back, those three lines read:

new_data_names_raw <- names(raw_data)
new_data_names_raw[1] <- "state_territory"
new_data_names <- new_data_names_raw

The third line copies the second variable into a third one and never touches it again. new_data_names is new_data_names_raw.

As n1 and n2 that was invisible, because nobody looks twice at n2 <- n1. Written out with names, it’s obviously a line doing nothing, and you can delete it.

That’s the argument for OK names in one example. I didn’t plant that line. I wrote it, and I didn’t notice it until I gave the variables names.

3.4 When two packages collide

This is a really common error, that I wanted to bring attention to in this script. Look at the top of the script again. Six library() calls, and further down it uses filter().

Which filter()?

Do you know what this message here is telling us?

library(dplyr)
#>
#> Attaching package: 'dplyr'
#>
#> The following objects are masked from 'package:stats':
#>
#>     filter, lag
#>
#> The following objects are masked from 'package:base':
#>
#>     intersect, setdiff, setequal, union

R is telling you that there are now two functions called filter(), two called lag(), and that when you type one of those names it will hand you the {dplyr} one, because {dplyr} was attached most recently.

Which means the meaning of your code depends on the order of the library() calls at the top of your script. And that’s a strange thing to be true.

Let’s quickly show that as it hits you - does this look familiar?

{MASS} also has a select():

library(dplyr)

Attaching package: 'dplyr'
The following objects are masked from 'package:stats':

    filter, lag
The following objects are masked from 'package:base':

    intersect, setdiff, setequal, union
library(MASS)

Attaching package: 'MASS'
The following object is masked from 'package:dplyr':

    select
starwars |> select(name, height)
Error in `select()`:
! unused arguments (name, height)

An error, straight away. Annoying. Familiar?

ImportantThis is why library() order is not a style question

Two scripts with the same lines in a different order can give different answers.

Worse, so can the same script run by two different people, if one of them had a package attached from a previous session. Which is one more reason for the blank slate settings in Project organisation 1.

3.4.1 The conflicted pkg to the rescue!

The {conflicted} package is built for this!

Instead of silently picking the last package attached, R refuses to pick at all:

library(conflicted)
library(dplyr)
library(MASS)
starwars |> select(name)
Error:
! [conflicted] select found in 2 packages.
Either pick the one you want with `::`:
• MASS::select
• dplyr::select
Or declare a preference with `conflicts_prefer()`:
• `conflicts_prefer(MASS::select)`
• `conflicts_prefer(dplyr::select)`

An error, at the line that is ambiguous, naming both candidates and telling you how to fix it. I think that is about as good as an error message gets.

You then say which one you meant, once, at the top of the script:

library(conflicted)
library(dplyr)
library(MASS)

conflicts_prefer(dplyr::select)
[conflicted] Will prefer dplyr::select over any other package.
starwars |> select(name)

This is a nice example of code that is documenting the reasoning.

You can also get {conflicted} to do a little reporting for you:

conflict_scout()

• `filter()`: dplyr and stats
• `lag()`: dplyr and stats
• `select()`: dplyr
TipGoing deeper: why not just write dplyr::select() everywhere?

You can, and some people do. It removes the ambiguity completely, and it is common practice in R package development.

I find in an analysis, it is a bit of noise. I have to look at this code a lot! A {ggplot2} plot block written that way is ggplot2:: down the left hand side of every line, and the shape of the code disappears behind a prefix that is identical on every row.

{conflicted} gets you the same safety without the tax, because the machine does the checking instead of you.

So should you use pkg::fun()? Maybe - here’s some thoughts on where it might be more worth it.

  • A package you use once for one utility, and don’t otherwise need attached.
  • Deliberately disambiguating at a single call site.
  • In R package development

3.5 A guide to reviewing code

The machine reviews the mechanics, the people review the thinking.

We talked about using the automated checks in air/styler and jalr/flir earlier - this means when you review code now, your attention is not on:

  • spacing
  • a misspelled comment, or
  • any(is.na(x))

Apply these tools!

3.5.1 1. Run the automated checks first

Before anyone reads it:

  • Format it. air format .
  • Lint it. jarl check . or lintr::lint_dir()
  • Spell check it. spelling::spell_check_files()
  • Run it from a clean session. Restart R, run from the top. If it doesn’t run, nothing else matters yet.

Only then is it worth a person’s time.

TipGoing deeper: if what you are reviewing is a package

Everything above works on a folder of scripts. If you are reviewing an R package, there is a tool that checks the habits a package is supposed to have:

goodpractice::gp()

It runs R CMD check, a set of linters, and a pile of structural checks - whether there is a README, whether the DESCRIPTION is well formed, whether functions are too long or too complex, whether there are tests.

It’s down here rather than in the list above because most of what it checks only exists in a package. Pointed at an analysis project, the great majority of its checks have nothing to look at.

Excellent tool, wrong shape for the code most of us review day to day. Worth knowing about for the day you write a package.

3.5.2 2. Read it top to bottom, and mark it up

Read the whole thing without fixing anything.

That’s harder than it sounds, because the urge to fix the first thing you see is strong. Resist it.

On this pass you’re only getting the shape of the thing, and collecting the places where the code caught you: where it didn’t quite make sense, where something was unclear, where you had to read a line twice.

Those moments are the data. Mark them and keep going.

Mark them with a word you can search for. I use two:

# TODO: this filter drops 400 rows and I do not know why
# NOTE: same block as line 40, with different columns

TODO for something that needs doing, NOTE for something you want to remember but which might turn out to be fine.

This beats holding it in your head for two reasons.

You can find them all again with a search, and both RStudio and Positron will collect them for you in a pane. And writing the note is far cheaper than fixing the thing, so you keep reading instead of disappearing down the first hole you find.

Steps 3 to 5 are the second pass, over the marks you just made.

3.5.3 3. Chunk it up

Here is a phone number:

1-8-0-0-1-3-1-0-8-6

Ten digits. Try to hold them in your head. Now try this:

1800 131 086

Same ten digits, and suddenly it’s easy.

Nothing about the information changed. Only the chunking did.

This is not a party trick. Working memory holds roughly seven, plus or minus two chunks at once, from George Miller’s 1956 paper “The magical number seven, plus or minus two”. Memory isn’t limited by the amount of information, but by the number of chunks.

So make bigger chunks and you hold more.

Code is the same, and the question to keep asking is:

How do I break this into pieces I can reason about one at a time?

3.5.3.1 Doing it to the script

Back to our ninety lines, now with the names fixed.

Read it once, and every time the subject changes, put in a blank line and a comment saying what just finished.

Don’t fix anything. You’re drawing lines, not editing.

Here is what I get:

# 1. read the raw spreadsheet for one year
# 2. fix the column names Excel gave us
# 3. pull out the education rows, make them long, drop the wide age bands
# 4. pull out the population rows, make them long, drop the wide age bands
# 5. join them, and work out the proportion studying
# 6. plot it

Six lines. That’s the entire script.

Ninety lines, six ideas, and I wrote those six down without understanding a single pivot_longer() argument. That’s what makes this move so useful: chunking does not require you to understand the code. It only requires you to notice where one thing stops and the next starts.

Now look at what falls out, for free.

Steps 3 and 4 are the same thing. Same slice(), same pivot_longer(), same arrange(), same five-line filter(). The only differences are which rows get sliced and what the value column is called. Forty lines doing one idea twice.

The change they asked for lives in step 1. Another year is another sheet in the same workbook, and nothing after step 1 cares which year it is looking at. But the year is baked into sheet = "2014", and educated_2014, and population_2014, and year = 2014 - so adding one currently means copying eighty lines and editing five numbers inside them.

Neither finding is subtle. Both were invisible in the wall of code, and obvious the moment it had six headings.

3.5.3.2 Then put like with like

Once you can see the chunks, tidy them:

  • All library() calls at the top.
  • All function definitions together.
  • If a variable is defined at line 10 and first used at line 150, move them closer.
  • Chunks that do similar things should sit near each other.
  • Add the commented headers, so the sections are visible without counting lines.
  • If a section is getting long, should it be its own script?

None of this changes what the code does. All of it changes how much you’ve got to hold in your head.

Two questions worth asking here: is the running order obvious to someone who has never seen it, and can you reason about each chunk on its own, or do you need the whole thing in your head at once?

TipWhere this script goes next

Those six comments are a to-do list. Each line is a function waiting to be given a name, and the two identical steps are one function called twice.

We pick the script up again in ?sec-writing-functions and take it the rest of the way, until adding a year is one argument rather than eighty copied lines. The whole progression, one script per step, is in the ozed repo.

3.5.4 4. Expression: can you follow it?

Now go back to the TODOs and NOTEs from step 2.

For each one: can you say what the code is for, in a sentence? Not what it does line by line. What it is for.

If you can’t, that’s the finding. Three things to look at when the answer is no.

3.5.4.1 What does it need, and what does it leave behind?

Two questions for any chunk: what does this need in order to run, and what does it leave behind?

A chunk that needs six objects made in four different places can’t be moved, can’t be tested, and can’t be understood on its own.

The other direction is easier to see, because you can mark it up in the file:

1penguins_raw <- read_csv("penguins.csv")
penguins <- clean_names(penguins_raw)

2n_total <- nrow(penguins)
n_missing <- sum(is.na(penguins$body_mass_g))
pct_missing <- n_missing / n_total

3mass_summary <- penguins |>
  group_by(species) |>
  summarise(mass_mean = mean(body_mass_g, na.rm = TRUE))

temp <- mass_summary |> arrange(desc(mass_mean))

ggplot(mass_summary, aes(species, mass_mean)) +
  geom_col()
1
Used further down. Fine.
2
Never mentioned again. Four objects, computed and abandoned.
3
Used. This is the actual work.

Four of the eight objects in that block are never read.

They aren’t harmless either. Each one is a name a reader has to hold, and a thing they have to check before concluding it doesn’t matter.

Usually it means somebody explored, found their answer, and left the exploring in.

Sometimes it means a result was supposed to be used and quietly isn’t, which is a bug rather than clutter.

A chunk with many inputs and many outputs is usually several jobs that happen to be sitting next to each other.

TipWill a linter find these for me?

Partly, and it is worth knowing exactly where the line is.

lintr::object_usage_linter() finds unused variables inside a function:

f <- function(x) {
  temp <- x * 2
  y <- x + 1
  y
}
#> warning: [object_usage_linter] local variable 'temp' assigned but may not be used

Run the same linter over the block above, sitting at the top level of a script, and it says nothing. pct_missing and temp go unmentioned.

jarl has unused_function and unreachable_code, but no unused-variable rule at the time of writing.

So at script level this one is yours. It is a good thing to look for precisely because no tool is doing it for you.

3.5.4.2 Is there a simpler form?

Sometimes code does something perfectly reasonable in a roundabout way, and R already has the direct version.

This happens most with statistics, because we were all taught the formula before we were taught the function.

  • Mean
  • Variance
  • Standard deviation
  • A linear model
  • Counting rows
  • Lengths of a list
sum(x) / length(x)

mean(x)
sum((x - mean(x))^2) / (length(x) - 1)

var(x)
sqrt(sum((x - mean(x))^2) / (length(x) - 1))

sd(x)
X <- cbind(1, d$x)
solve(t(X) %*% X) %*% t(X) %*% d$y

coef(lm(y ~ x, data = d))
nrow(d[d$mass > 4000, ])

sum(d$mass > 4000)
sapply(my_list, function(i) length(i))

lengths(my_list)

Each pair gives the same answer. The second one says what is being computed, and the first says how, which is a detail the reader has to decode before they can get to the meaning.

The lm() one is the sharpest, because the long version isn’t wrong. It’s the normal equations, it’s what lm() does, and somebody wrote it out because that’s how they learned it.

It’s also less numerically stable than lm(), has no standard errors, and takes a reader thirty seconds to recognise.

You can’t spot these unless you happen to know the shortcut, which is a bit unfair. So don’t go hunting. Just notice when a line feels like more machinery than the idea deserves, and go and look.

3.5.4.3 What would break if the data changed slightly?

An extra column. A new NA. A factor level nobody expected. A year that is not in the file.

Code that only works on the exact data in front of it is worth a NOTE, even when you’re not going to do anything about it today.

You do not have to fix anything. Counting is the exercise.

3.5.5 5. Re-expression: refactoring

The last question is the useful one.

Can you re-express the intention of the code, and keep the output the same?

That’s refactoring: changing code while keeping its behaviour.

It’s like giving a car a service, or replacing parts that have worn. The car drives the same, it just does it more reliably.

This is where everything you marked gets cashed in. The copied block becomes a function. The four abandoned objects get deleted. The normal equations become lm().

Then you run it again and check the output hasn’t moved.

That check isn’t optional. It’s very easy to tidy something into a different answer.

TipCode smells

A code smell is a bit of code that is not wrong, but that makes you uneasy.

The word is deliberate. It is the feeling of opening the fridge and knowing something in there has gone off before you have worked out what.

Smells are useful because they’re cheap. You don’t have to prove anything to act on one.

You notice that a function is doing three things, or that a block has been copied twice with one number changed, and you write a NOTE. Refactoring is what you do about it.

For a great introduction, watch Jenny Bryan’s “Code smells and feels”.

One more question worth asking before you finish: is anything here that you could regenerate? And the other way round, is anything precious sitting somewhere disposable?

3.6 Reviewing someone else’s code

Everything above works on your own code.

Doing it to someone else’s is a different skill, and most of the difference is social rather than technical.

Ask what they want first. Before reading a line: what kind of feedback are you looking for? Someone who wants to know whether the statistics are right does not want thirty comments about variable names. Then: what is this code meant to do? Find the intention before you review the implementation, because half of what looks like a mistake turns out to be a decision you did not have the context for.

Review the code, not the person. “This function is doing three things” is useful. “You always overcomplicate things” is not.

Say what is good, specifically. This is not politeness. If you only ever name problems, people learn what to avoid and never what to aim for.

Run it, don’t just read it. Then run it on something slightly different from what the author used. Your data, an extra column, a year that is not in their file. Reading tells you whether code is comprehensible; running it on something unfamiliar surfaces the assumptions the author did not know they were making.

It will be slow at first. Your first few reviews will take ages and feel thin. That’s what reviewing is like at the start. The people who spot things instantly have simply read a lot of code.

TipWhen it breaks and you cannot see why

Cut it down. Remove everything not needed to make it fail, one piece at a time, until what’s left is small enough to see through.

That is a review technique, and it is also exactly how you make a reprex. We come back to it in Writing a reprex / getting unstuck.

TipIf you want to see this done at full scale

Open software peer review is the most developed version of this practice, and it is all public. rOpenSci’s reviewer guide sets out what a reviewer is asked to look at, and their review template is the checklist itself. Reviews happen in the open on GitHub and are signed, so you can read hundreds of real ones.

Two things there are worth stealing for a small analysis project. Reviews are explicitly non-adversarial, because the goal is better software rather than a verdict. And reviewers are asked about things a checklist cannot capture, such as whether the argument names read well and autocomplete sensibly.

That last one should sound familiar from the naming section.

TipIf we can see your code, we can trust it

Version control is not part of this course. It has its own.

But the single biggest improvement to reviewability is putting your code somewhere it can be seen, with a history. Review is much easier when the reviewer can see not just what the code is, but how it got that way.
